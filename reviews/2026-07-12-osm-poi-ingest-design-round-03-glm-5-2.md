1. CRITICAL | §3, Taxonomy | The `mooring=*` kind in `canal_service` silently captures `mooring=no` as a mooring POI unless parsed-elsewhere; saying "except explicit `no`" is a classifier detail, but the model `PointOfInterest` has no accessibility flag and validation never rejects `mooring=no` records. REQUIRED EDIT: Add validation that a `mooring` record with `source_tags.get("mooring") == "no"` is excluded during classification or hard-rejected in artifact validation, and state which layer enforces it.

2. HIGH | §4, Data Contracts | `PointOfInterest.nearest_edge: tuple[int, int]` is non-serializable for Pydantic and JSON-friendly output; more importantly it is not guaranteed immutable/hashable, and `GraphArtifact` relies on tuple POIs that are themselves frozen-but-not-hashable. REQUIRED EDIT: Document that `PointOfInterest` is a frozen Pydantic model and coerce `nearest_edge` to a fixed-length tuple during validation (or split into `nearest_edge_low_uid`/`nearest_edge_high_uid`) so the artifact payload stays deterministic and unhashable mutable sequences cannot leak into the pickle.

3. HIGH | §6, Runtime Spatial Lookup | The STRtree-query expanding-radius contract guarantees correctness only if the initial longitude/latitude envelope contains the complete spherical circle; but the spec never specifies how `min_uid`/`max_uid` representation in the edge tree interacts with node-tree expansion whose sort key is `(distance, uid)`, leaving tie-break behavior ambiguous across the two phases. REQUIRED EDIT: Add a sentence pinning the node-STRtree returned-UID mapping to stable per-instance indices or a `dict[geom_id, uid]` table so re-querying after box doubling cannot reorder candidates, and explicitly state that the edge tree is unaffected by node expansion.

4. MEDIUM | §7, Artifact Validation | Validation requires `projected points are consistent with the attached edge within a documented numeric tolerance` but no tolerance value is named, and the metric is in EPSG:27700, so reproducible review cannot confirm the check. REQUIRED EDIT: Name the tolerance (e.g., `1e-3 m`) and state the metric (Cartesian distance between the stored projected point and the closest point on the stored edge line in EPSG:27700) within Section 7.

5. MEDIUM | §5, Geometry and Data Flow | The waterway-corridor filter is distance-to-edge in EPSG:27700, but the edge STRtree is built from waterway edges only, while `nearest_waterway_distance_m` validation in §7 compares against the category threshold; no rule states whether `WaterwayFeatures` includes non-navigable edges, so an OSM waterway tagged `waterway=stream` could produce a misleadingly small `nearest_waterway_distance_m`. REQUIRED EDIT: State within §5 or §7 that the STRtree contains only the same navigable-edge subset used for routing, and define a validation failure if a retained POI's nearest edge is not navigable.

6. MEDIUM | §2, Decisions | "Do not import parking" conflicts with no validation hook that rejects records whose classified kind is `parking`; the classifier skips unknown values but parking tokens like `amenity=parking` are in a known OSM namespace and could be misrouted by a future code path. REQUIRED EDIT: Add either an explicit negative allowlist condition in §3 defining `parking` as a rejected kind, or state explicitly that `amenity=parking`/`parking=*` are unknown to the classifier and thus counted under `unknown_value`.
